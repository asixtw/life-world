## 二、Life World 的產品定位

產品名稱：Life World。核心理念：

> 透過現實中的努力，打造一個屬於自己的世界。

Life World 結合 AI 輔助、目標管理、行動紀錄、個人成長與虛擬世界回饋。使用者設定現實目標，透過 AI 協助規劃行動、整理紀錄及分析進展，將經確認的成果轉換成寵物成長、食物、裝飾或其他回饋。

核心流程：設定目標 → 規劃行動 → 記錄真實經歷 → AI 協助理解與整理 → 使用者確認 → 更新進度 → 獲得虛擬回饋。

努力應被看見，未完成任務不應造成懲罰。情感原則是「你可以暫時離開，但你的世界永遠歡迎你回來。」不得設計寵物死亡、長時間未登入扣分或造成過度壓力的懲罰機制。

## 四、產品與設計原則

### 使用者體驗優先

設計前先確認誰會使用、希望完成什麼、在什麼情境使用、最少操作步驟、優先資訊，以及可能造成誤解、錯誤或焦慮的操作。不要直接從功能清單開始畫介面。

### 簡潔而不簡陋

提供清楚的資訊層級、一致元件、適當留白、易懂導覽及明確主要操作；補齊成功、失敗、載入與空白狀態，兼顧手機、桌面及基本無障礙。避免為視覺效果增加不必要的動畫、裝飾或操作成本。

### 統一設計系統

共同維護色彩、字體、間距、版面、按鈕、輸入框、卡片、對話框、導覽、資訊架構、圖示、插畫、回饋動畫及互動狀態。

奶油白、薄荷綠、天空藍、暖黃色及柔和紫色為候選方向；正式色票與元件以團隊核准文件為準。目前 App 沿用暖白／薄荷，虛擬世界以溫暖、簡潔的 2D 寵物與房間為方向，不過早發展複雜 3D 系統。

### 產品一致性高於單一畫面美觀

新畫面必須對齊既有導覽、元件、資料狀態及流程；衝突時先指出差異與調整方案，不直接另創風格。

## 五、AI 功能設計原則

AI 必須解決明確問題，不為展示 AI 而加入功能。優先考慮自然語言目標拆解、行動紀錄分類與結構化、文字／語音摘要、圖片資訊擷取、下一步建議，以及紀錄缺漏與異常檢查。

AI 結果原則上是草稿。涉及客戶資料、目標進度、正式經歷或後續任務的更新，必須提供人工檢查與確認；不能虛構客戶資料、學習成果、已完成任務或使用者未提供的事實。

研究時區分現成模型／API、提示詞設計、檢索增強及實際模型微調。不得把串接 API 描述為自行訓練模型。微調必須具備資料集、基準模型、訓練設定、獨立測試集及前後比較。

虛擬獎勵優先採可解釋、可測試的固定規則，不讓 AI 任意決定獎勵。

## 六、軟體開發的共同紀律

統一順序：**確認需求與邊界 → 設計架構及必要介面 → pytest 測試 → 執行確認失敗 → 正式實作 → 測試通過 → 必要重構與回歸驗證 → 一致性審查。**

### 需求、架構與介面

開發前列出使用者問題、輸入／輸出、核心流程、成功標準與不在本次範圍內的功能，並列出正常、異常及邊界情況。

確認模組責任、資料流、依賴方向、資料庫結構、API 契約及錯誤處理；先定義必要資料結構、型別、介面及不可違反的條件。介面未定時不大量產生實作，也不讓不同成員自行假設格式。

必要時可建立可匯入的最小骨架以執行測試，但不在測試之前完成正式邏輯。

### 八點開發紀律

1. **先列需求及邊界**：明確說明輸入、輸出、成功條件及排除範圍；資訊不足時先查現有文件與程式，重要歧義再確認。
2. **先寫測試**：Python 功能與錯誤修正先用 pytest 撰寫正常、異常及邊界案例。依影響加入錯誤輸入、空白資料、重複提交、API 失敗、權限錯誤、交易一致性及 AI 輸出不完整／錯誤案例。
3. **確認紅燈原因**：實際執行，確認失敗源於功能缺失或行為錯誤。環境、依賴或設定失敗另列，不冒充有效的功能紅燈。
4. **再寫正式程式**：依已確認需求、介面與測試標準分批實作，維持既有風格、資料模型與模組邊界，不擅自更換框架或新增重大依賴。
5. **失敗後修正重跑**：保留原需求及驗收標準，不得偷偷刪案例、放寬斷言或跳過失敗測試。若測試本身有誤，先說明依據與影響，不把修正測試當作降低標準的捷徑。
6. **據實回報結果**：列出實際命令、通過／失敗／跳過數與限制。無法實際執行就說明原因及未驗證範圍，不宣稱通過；歷史測試不冒充本輪執行。
7. **驗證完整流程**：前端流程需適當的瀏覽器操作及手機／桌面畫面驗收，不能只以 pytest 通過代替 UI 流程對齊。測試失敗修正後重新執行受影響案例及必要回歸。
8. **加入繁體中文註解**：新增及修改的自有程式碼、測試與工具腳本逐行補上有意義的中文註解，說明用途或規則，優先放在行末。

註解使用各語言合法語法。跨行字串、SQL／HTML 模板及無註解語法的格式，在相鄰合法位置逐段說明，不把註解寫入實際資料、不破壞語法，也不顯示在產品畫面。空白行不加註解；第三方及自動產生檔不直接改寫。既有導讀與說明見[中文註解指引](CODE_GUIDE_ZH.md)。

探索性 UI 原型不必把所有視覺程式都硬套 pytest，但核心資料規則與跨模組契約仍須有驗證方法；Python 正式功能與錯誤修正遵循上述 TDD。純文件整理不為了湊 TDD 而新增沒有產品用途的 Python 程式，以內容、連結及差異檢查驗證。

### 執行與一致性審查

後端命令為 `.venv/bin/python -m pytest -q`；瀏覽器命令為 `.venv/bin/python -m pytest browser_tests -q -x --tb=short`，須依 [README](../README.md) 啟動隔離測試服務，不指向真實使用者資料。

每完成一個主要功能閉環，或約三個相關模組，審查需求符合度、介面相容、必要測試、設計系統、安全／隱私及不必要複雜度。結果記入[驗收紀錄](ACCEPTANCE.md)，功能變化更新[演進紀錄](EVOLUTION.md)。

## 十一、最高原則

Life World 的目標是讓使用者願意回來，協助現實成長，透過虛擬世界提供正向回饋，不是追求功能最多。

每個決策同時考量使用者價值、體驗一致性、技術正確性、可維護性、團隊交付能力與長期擴充性。品質與時程衝突時，優先保護核心流程正確性，明確說明縮減範圍的代價。

不要只把功能做出來，要協助團隊把正確的產品做好。
