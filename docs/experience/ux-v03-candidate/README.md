## 設計要點

1. 四步沿用 v0.2：經歷來源 → 目標活動量 → 直覺的人物選擇／新姓名／互動分類 → 摘要確認。沒有第五步。
2. 第三步不展示長人物維度、故事標題、原文索引或 CRM 表單；原文提及透過來源抽屜核對。
3. 第四步不重複第三步。人物卡預設僅姓名、建立／更新狀態與角色；點擊開本次變更抽屜，逐項候選、取消與來源。新人物沒有來源的欄位不憑空顯示。工作／公司有原文才列入「目前不寫入」區，合併說明能力缺口，不可勾入保存。已核對且具保存能力的項目才進「確認後會保存」；多人定向提交未接通的資訊仍留在不寫入區。
4. 人物更新分人處理；興趣多值採「保留原有 ＋ 新增」展示，不假裝覆寫既有事實。原文實質改動會保留摘要但要求重新核對，AI 候選保守失效；無關且來源仍有效的手動資料盡量保留。未改原文的返回不取消核對。
5. 「刪除已保存草稿」與「捨棄未保存修改」有不同入口、告知與回饋；列表／編輯選單可刪，失敗保留、可重試／重載。
6. AI 整理只選「直接使用原文／使用 AI」，預設手動。首次外部草稿授權揭露 Google Gemini（示意設定）、文字範圍與用途；相同範圍有效不重問，背景授權不混用。AI 失敗保留原文，可回手動；Demo 不會呼叫模型。
7. **正式產品沒有正式帳號／訪客模式頁籤。** 本地 Demo 的 Session 情境選擇只在可收起的「設計審查工具」，不屬產品 UI。正式接線必須讀實際 Session／capabilities，不能以本機開關取得權限。
8. 訪客有精簡狀態與保存入口；正式帳號只有帳號選單。保存我的世界＝PR22 upgrade 同 Owner、同一步、保留輸入，第三步只局部解鎖人物；登入以前的世界＝次要獨立流程，明確同意後才交換到既有 Owner，不承諾帶入訪客表單。能力未啟用沒有無效按鈕。

## 如何審查

直接開 index.html。從「設計審查工具」選擇情境即可檢查所有空白、失敗、人物變更、草稿與帳號畫面。選「第三步訪客」→ 保存我的世界 → 模擬 Google 驗證，可觀察停留第三步並立即解鎖人物；用工具切換取消／驗證失敗／衝突，輸入仍保留。這些只展示互動，沒有真 Google 或假 Token。

Demo 沒有 fetch／外部服務、Cookie、LocalStorage、資料庫寫入或真 AI。重新載入會重置樣本。模擬確認／刪除成功只改記憶體，不代表正式產品功能已實作。請勿在樣本輸入真實個資。
