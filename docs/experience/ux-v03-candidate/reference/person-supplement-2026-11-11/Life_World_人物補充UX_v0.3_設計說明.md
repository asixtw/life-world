# Life World｜人物補充 UI/UX v0.3 延伸候選

狀態：**Candidate / NOT APPROVED**。此原型為獨立 HTML，沿用 v0.3 第 3／4 步的視覺方向。不修改 GitHub PR、API、資料庫或正式產品。

## 使用者問題

每次記錄經歷時，使用者可能剛得到一項關於人物的新資訊。如果必須先保存經歷、再到人物詳情頁編輯，容易遺漏；但若直接攤開完整人物表單，又會妨礙純日記與簡單活動紀錄。

## 建議流程

1. 第 3 步：選擇「不關聯人物」或「有相關人物」。
2. 有相關人物：選既有人物或新增人物；逐人選「直接互動／共同參與／僅提及」。
3. 每張人物卡提供可選的「補充人物資訊」，預設收起。
4. 可補充現有契約的已確認維度（本原型示範 interests、food）及公司／職稱／生日候選。每項資料都歸屬特定人物。
5. 第 4 步：人物卡可點開底部抽屜；顯示本次候選、確認勾選、資料來源，以及「目前不寫入人物檔案」的欄位。
6. 最終確認後才可以正式更新；退出／取消／返回時不能偷偷新增人物或覆寫經歷。

## 驗收重點

- 純日記零人物，可直接到第 4 步。
- 補充資訊完全選填；不強迫開展全部欄位。
- 多人物的欄位、角色、勾選狀態各自獨立。
- 第 4 步只顯示差異與來源，不重新放整張編輯表單。
- 未勾選、沒有來源或資料不明的資訊不得寫入正式人物事實。
- 新人物建立需等最終確認；未確認前取消不留孤立人物。
- 來源改變時需標記相關候選重新核對，不能保留舊核准狀態。
- 目前 `people`/`person_facts` 並沒有獨立公司、職稱、生日欄；**本 Demo 僅展示候選，不代表真的儲存成功**。這些欄位的正式儲存需先經團隊核准契約與 Migration。
- 此 Demo 使用假設資料，按確認僅顯示模擬提示，完全沒有持久化、權限、Google 升級或真正 AI。

## 設計取捨

保留原四步、不增加第五步；先使用者主動選人物，再讓他自行決定是否進階編輯。人物資訊要逐漸立體，不等於每段經歷強迫填完人物履歷。

## 工程邊界

正式接線前須先完成候選狀態與後端 payload 一致性、多人定向更新、安全交易、來源撤回等相關契約；本原型沒有驗證正式 API。
