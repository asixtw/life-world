## 2. 逐頁畫面契約（預設狀態不出現大型進階表單）

### 01｜記錄經歷
- 優先「文字／拍照與影像／語音」三入口；訪客僅文字。可組合來源，原文不因 AI 改寫。
- 只處理內容與素材。原文、發生時間與來源有清楚位置；可選 AI 但不得強制。
- 無論返回、切入口、網路錯誤，不遺失輸入。

### 02｜目標與活動數量
- 「不關聯目標／有目標進度」清楚可選。
- 選目標及輸入實際數量；數量須人工確認，不得 AI 直接推斷。
- 不要求純日記硬選目標。

### 03｜人物關聯
- 首先只問「這次有和誰互動，或在經歷中提到了誰？」可選「不關聯人物／有相關人物」。
- 主要操作：「選擇既有人物」及「＋ 新增人物」，新人物最少只填稱呼。
- 使用生活語言讓使用者區分：**有直接互動／一起參與但未互動／只是提及**。多人可以逐個新增。
- **不要**預設展示故事標題、原文索引、進階 checkbox 清單、全部人物維度與長 CRM 表單；只有需要時展開次要細節。
- 同名需提示人工區分，不自動合併。正式人物只能在第 04 步確認後建立。

### 04｜檢視並確認
- 上方顯示可編輯的本次經歷摘要；原始文字/素材可展開檢查但不覆寫。
- 下方僅顯示簡短「目標與進度摘要」「人物關聯摘要」「下一步（選填）」；各區有**真正可操作**的修改入口。
- 人物以可點擊卡片／清單列出：**姓名、建立／更新狀態、實際參與／直接互動／提及角色**。
- 點擊某人物展開或開底部抽屜：**本次人物資料變更預覽**，只顯示本次將建立、增加或更新的值，不預設顯示完整人物編輯表單。
- 新人物：顯示「待建立」、姓名、角色與本次經使用者確認後將保存的欄位；沒有來源資料的興趣／職稱／公司不可憑空展示。
- 既有人物：如本次存在變更，明示「舊值 → 新候選值」或「新增資訊」，可勾選／取消候選並有「查看來源」。沒有變更時顯示「本次只有經歷關聯，不修改人物資料」。
- 一段經歷多位人物時，每位人物獨立預覽與確認，不把資訊偷偷套用到第一個人物。
- 明確區分 **使用者輸入、AI 候選、已確認資料、僅供內部動態分類**；AI 候選不因預覽而正式寫入。
- 職稱、公司為本次期望預覽的例子，但現有 PR #24 的 `pending_person` 只支援姓名/關係，且正式更新 schema 尚無獨立 company/job 欄。**若無可寫入契約，不得預覽成「將保存」；先提出最小 schema/資料契約與 UI 落差，等待核准。** 不得塞入 tags/notes 冒充獨立欄位。
- 只有最後人工確認才發生正式寫入；取消、重試、回上一頁不新增人物、不計分。

## 3. 草稿生命週期（必須可完成，非文字說明取代操作）

- 保存草稿：可回來繼續編輯，不代表正式經歷。
- 捨棄未保存修改：只捨棄本次未保存變更，不等於刪除已存伺服器草稿。
- **刪除草稿（正式操作）**：草稿列表與編輯頁均有可理解入口；二次確認後只刪 `status=draft` 且屬同 Owner、版本符合的草稿；不得刪已確認經歷。處理 draft_stories、媒體本機引用以及失敗重試；不能僅呼叫 `MediaUI.discard()`。
- 顯示刪除進度、成功、失敗與版本衝突；不可先跳轉再宣稱刪成功。
- 需設計防止誤刪的完整 API 契約和測試。

## 5. 合併阻擋（Owner Design Gate）

- Gate A｜**設計審核**：Codex 先交「四步的手機與桌面截圖＋互動 Demo＋差異表」；Owner 親自判定 `Approved / Changes Requested`。在批准前不要把 UI 當作完成，不要宣稱跟 Wireframe 相符。
