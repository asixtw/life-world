# Unified Person 階段交接說明

更新：2026-11-11（第四輪，依獨立驗收修正）。分支 `jerry_unified_person`（不合併到 main）。這份文件給接手的開發者：這個階段做了什麼、程式在哪裡、怎麼驗證、還沒做什麼。

## 1. 這個階段完成的功能

| 功能 | 畫面 | 主要程式 |

| 人物設定（五區塊九欄位，每次儲存新增一版） | 人物頁「人物設定」頁籤、編輯頁 | 同上 |

| 左側導覽：世界／目標／紀錄／人物／作品 | 全站 | `app/static/app.js`（`navigation`）、`persons.js`（`legacyNav`） |

人物頁網址是 `#persons/{id}?tab=overview|profile|experiences|relations`。人物列表的卡片整張可點，進入人物頁；完整的編輯表單只從人物頁的「編輯人物」進入。

兩條主要的填寫流程（2026-11-11 第三輪定案）：

- **人物 → 我的設定**：進入「人物」，最上方是「我的設定」卡片（還沒建立時是「建立我的設定」），下面才是搜尋與人物列表。搜尋、篩選、翻頁或看封存時不顯示這張卡片。我的設定頁歸在「人物」底下，返回連結回人物首頁。
- **紀錄 → 我的經歷**：進入「紀錄」，第一個頁籤是「我的經歷」→「＋ 新的經歷」→ 記下 → 核對 → 確認 → 回到我的經歷。

畫面上的名稱在這一輪改過：「我的紀錄」改稱「我的經歷」，「我的人設」的頁面與入口改稱「我的設定」。程式、API 與資料表的名稱沒有改（`experiences`、`self_persona`、`/api/self-persona`）；後端的同意文字與作品建立流程裡仍寫「我的人設」，我的設定頁上有一行說明兩者是同一份資料。

左側導覽在人物系統可用時不再列出舊的「關係」「角色」。這兩個頁面沒有刪除：`#people`、`#person/{id}`、`#characters` 仍可由網址進入，作品建立流程裡也有前往角色卡的連結。人物系統不可用（資料庫還沒升到 010、或不是以 `link_table` 部署）時，導覽維持原本的入口。

## 2. 資料分類原則（已裁決，請沿用）

- **我的經歷**（2026-11-11 前畫面上稱為「我的紀錄」）：使用者本人實際參與的生活紀錄。走草稿 → 核對 → 確認，會計入積分與目標。只能關聯真實人物。資料表 `experiences`。
- **人物經歷**：以人物為主體的經歷，使用者不必參與；性質是真實、歷史或虛構。直接儲存，不計積分、目標與互動統計。資料表 `subject_experiences`、`subject_experience_people`。
- **我的設定**（資料上的名稱是「我的人設」）：使用者本人的設定，給 AI 扮演「我」時使用。一個帳號一份，每次保存新增一版，要另外按「我同意」才會送給 AI。資料表 `works`、`work_versions`（`kind='self_persona'`）、`data_consents`。
- **作品**：作品內的場景、演出職稱與演出內容。這個階段沒有動作品。人物是獨立的；作品裡的演出職稱不是人物，也不回寫人物設定。
- 共同參與不會自動建立人物關係；新增經歷不會自動修改人物設定。

## 3. 資料模型（Schema 010，這個階段沒有新增資料表或欄位）

- `people`：人物主檔（含 010 的 `aliases`、`person_type`、`person_subtype`、`description`、`origin_type`、`status`）。
- 人物設定存在 `notes`（`kind='preparation'`、`title='person_profile.v1'`），內容是 JSON：`{schema, version, previous_id, origin, generation_id, fields}`，`fields` 有九個 key：`background`、`personality`、`motivation`、`stance`、`abilities`、`expression`、`behavior`、`knowledge_boundary`、`restrictions`。
  - 只新增不更新。正式版本靠 `requests` 的回執辨識：`operation='persons:profile:{person_id}'`，`response.id` 等於那一版的 `notes.id`。沒有回執的同格式筆記只是私人筆記。
  - 欄位上限：背景 3000、性格 2000、動機／核心信念／能力／固有限制 1500、行為模式 2000、說話與表達方式 2000、知識範圍 1000。
- `person_connections`：同一對人物只有一筆；`relation_types`（最多 10 種，API 只讀寫 `kind`）、`description`（雙方共用）、`confirmation_status`（`archived` 表示封存）、`revision`。
- `person_connection_experience_sources`：關係來源，一列指向一筆我的經歷或一筆人物經歷，`source_position` 保存順序。
- `subject_experiences`：`experience_type`（real／historical／fictional，建立後 App 不能改）、`title`、`raw_text`、`occurred_at`＋`occurred_precision`（unknown／year／month／day）、`occurred_label`、`status`、`revision`。
- `subject_experience_people`：`role` 是 `subject` 或 `participant`。一筆經歷一位主體、0 到 50 位參與人物。
- 我的人設的內容（`work_versions.content_json`）有十二欄加真實程度：`display_name`、`public_profile`、`personality`、`speaking_style`（四欄必填）、`motivation`、`values`、`behavior`、`knowledge`、`relationships`、`boundaries`、`appearance`、`sample_lines`（最多 3 句）、`truth_level`（real／mixed／ideal）。欄位名稱和人物設定的九欄不同，兩者沒有合併。

## 4. API

| 方法與路徑 | 用途 |
|---|---|
| `GET/POST /api/persons`、`GET/PATCH /api/persons/{id}`、`POST /api/persons/{id}/status` | 人物列表、新增、讀取、編輯、封存／恢復 |
| `PUT /api/persons/{id}/profile` | 儲存一版人物設定（`expected_profile_id` 防覆蓋） |
| `POST /api/ai/generate`（module `person_profile`） | AI 產生人物設定候選 |
| `POST /api/people/{id}/connections`、`PATCH /api/connections/{id}` | 建立、編輯、封存、恢復關係；`source_experience_ids` 與 `source_person_experience_ids` 各自獨立 |
| `GET /api/persons/{id}/connection-sources?other_person_id=` | 可引用的來源（我的經歷＋人物經歷） |
| `GET /api/persons/{id}/experiences` | 人物頁「經歷」頁籤的兩區資料 |
| `GET/POST /api/person-experiences`、`GET/PATCH /api/person-experiences/{id}` | 人物經歷總列表、新增、讀取、編輯、封存／恢復 |
| `GET /api/generation/people` | 建立作品可以選的人物：本人使用中的人物，附最新正式人物設定的識別碼與版號（沒有設定的 `profile` 是 null） |
| `POST /api/generation/runs` | 建立作品。`setup.participants[]` 的 `source` 可以是 `person`（`ref: {person_id, profile_id?}`）或 `card`（`ref: {work_id, version_no}`） |
| `POST /api/series`、`GET /api/series/{id}` | 把已完成的作品開成多章節作品（它是第 1 章）；讀取作品總覽（已定稿的章節、草稿） |
| `POST /api/series/{id}/episodes` | 續寫下一章：建立草稿作品並開始生成（只需要這一章的場景；人物、風格沿用整部作品） |
| `POST /api/series/{id}/episodes/{作品}/adopt` | 採納草稿成為主線的下一章 |
| `GET/POST /api/works/{id}/exports` | 列出、建立作品的匯出（目前只有 `format: html`）。內容沒有變時回最新那一筆，不新增 |
| `GET /api/works/{id}/exports/{版本}/download` | 下載那一次匯出的檔案（附件） |
| `GET/PUT /api/self-persona`、`POST /api/self-persona/consent` | 讀取、保存我的人設（已有人設時要帶 `expected_revision`）；同意或撤回給 AI 使用 |

寫入都帶 `request_id`（重送回原結果）與 `expected_revision`（版本不符回 409）。

### 資料完整性的後端規則（2026-11-11 第四輪修正）

| 規則 | 在哪裡檢查 | 不符合時 |
|---|---|---|
| 我的經歷的關聯人物與故事參與人物，只能是使用中的真實人物（歷史人物、虛構人物一律拒絕） | `service.py` 的 `_recordable_person`，由 `_related`（草稿建立、草稿修改、確認）與 `connections.py` 的 `_validate_story` 呼叫 | 422 `person_not_recordable`；人物已封存回 409 `person_archived`。拒絕發生在寫入之前，不會留下草稿、經歷、積分或目標進度 |
| 被人物關係引用為來源的人物經歷，不能封存，也不能把參與人物改到和那段關係無關 | `person_experiences.py` 的 `patch_person_experience` → `relation_sources.require_still_related` | 409 `relation_source_in_use`，訊息會指出是哪一段關係；經歷、關係、來源都不變 |
| 被人物關係引用為來源的我的經歷，更正故事參與人物後仍要和那段關係有關 | `connections.py` 的 `edit_story_people` → 同一個檢查 | 同上 |

補充：

- 名單裡只要有一位不合規，整筆請求拒絕，不會部分成功。
- 已經確認的舊經歷不追溯：更正舊故事時，原本就在名單裡的人物可以留著，但不能再加入不合規的人物。
- 人物類型是 Schema 010 的欄位，所以第一條規則只在 `link_table` 模式生效；舊結構沒有類型可查，維持原行為。
- 使用者要先到那段關係移除來源，才能封存或修改經歷。已封存的關係也算引用。
- 前端的篩選（記下經歷時只列真實人物）只是方便選擇，不是防護。

### 作品引用人物（2026-11-11）

建立作品的「① 人物」在人物系統啟用時先列人物；舊角色卡收在可展開的區塊裡，仍然可以選，也可以和人物混用。沿用原本的雙人／多人文字生成流程（規劃、逐段生成、保存、恢復），只多了一種人物來源。

| 規則 | 在哪裡 | 不符合時 |
|---|---|---|
| 只能選本人使用中、而且有正式人物設定（有回執、九欄不是全空）的人物 | `roleplay.py` 的 `_person_member`（建立作品的交易內，寫入之前） | 404 `not_found`（別人的或不存在）、409 `person_archived`、409 `person_profile_required` |
| 開始時鎖定當下最新的正式人物設定：記下人物、人物設定的識別碼、版號與九欄內容的雜湊 | 同上，寫進作品的 `meta.participants[]` | 畫面送來的 `profile_id` 不是最新版：409 `person_profile_changed` |
| 每一段生成前重讀鎖定的那一版，必須仍是正式版本、版號與雜湊相同 | `_person_persona` | 作品停止（`source_unavailable`），已生成的段落保留 |
| 規劃階段和其他人物只看得到公開簡介（人物簡介，沒有簡介就用身分；最多 400 字） | `_person_member`、`_public` | — |
| 同一位人物不能重複選；人物和角色卡同名不能一起出場 | 輸入模型、`start_generation` | 422（`duplicate_cast_name`） |

補充：

- 輪到人物發言時，送給模型的人格是姓名、類型（`kind`：fictional／real／historical）、公開簡介，加上九欄。九欄沿用原本的欄位名稱，只有「固有限制與弱點」以 `weaknesses` 送出：它描述人物本身，不是演出規則，沿用 `restrictions` 會和角色卡的「禁止事項」混淆。
- 人物之後另存的新版本不影響進行中的作品；新建立的作品才用新版本。封存人物不會停止進行中的作品（和角色卡相同），但不能再加入新的作品。
- 同名的舊角色卡、格式相同但沒有正式回執的筆記，都不會取代正式人物設定。
- 生成紀錄的 `input_json.persona_ref` 記的是來源：人物來源是 `{source, person_id, profile_id, version, content_sha256}`。它不是送給模型的完整內容；要證明模型實際收到什麼，用本機的擷取型假模型測試（`tests/test_person_source_generation.py`）。
- 生成不寫回人物、人物設定、我的設定、我的經歷或積分。
- 真實人物也可以選（沿用「連真人不另要求同意」的裁決）；作品仍是虛構演出。

### 作品匯出成 HTML（2026-11-11，第 1 級：純文字）

方向：所有作品之後都以「可下載的 HTML」交付。劇情（之後還有圖片）由模型生成並保存；HTML 的程式是固定的播放器，不是每次生成；匯出只是把已保存的內容打包，不呼叫模型。這一級把整條路走通：已完成的文字作品 → 單一 HTML 檔 → 存進 Cloud Storage → 留下匯出紀錄 → 下載 → 離線開啟。

| 規則 | 在哪裡 |
|---|---|
| 只有本人、已完成的生成作品可以匯出；其他一律 404 或 409 `work_not_completed` | `work_export.py` 的 `_export_source`、`create_work_export` |
| 同一個作品版本配同一個播放器版本，產出的檔案逐位元相同；檔名用內容雜湊，相同內容只存一份、只記一筆 | `render_html`、`create_work_export` |
| 檔案不引用任何外部資源；內嵌的樣式與程式用 CSP 雜湊鎖定；作品文字一律跳脫 | `render_html` |
| 檔案裡只有作品本身（標題、前提、場景描述、人物名稱與角色定位、逐段內容），不放人物設定、我的設定、公開簡介、演出要求、場景條件 | `story_data` |
| 下載時核對擁有者，並比對檔案雜湊與紀錄；以附件送出並加上 sandbox | `work_export_file`、`install` |
| 檔案只能寫進這個環境自己的 bucket；設定和白名單不一致就不開放 | `object_storage.py`、`environment.py` 的 `works_bucket` |

補充：

- 匯出紀錄沒有新增資料表：每個作品對應一列 `works`（`kind='work_export'`，識別碼由作品識別碼以 UUIDv5 推導），每次內容不同的匯出新增一個 `work_versions`，內容是檔案清單（物件路徑、雜湊、大小、來源作品版本、播放器版本）。作品中心不列這種作品。
- 播放器在 `app/export_player/`（`reader-1.css`、`reader-1.js`）。內容直接寫成 HTML，程式只處理字級、深淺色、場景提示；不能執行程式的預覽工具也讀得到內容。要改樣式或行為時換新的版本名稱，舊的匯出檔不受影響。
- 檔案裡另外嵌了一份劇情資料（`lw-story.v1`），之後的圖文、互動播放器會從這份資料繪製。
- 物件儲存直接走 HTTPS 呼叫 Cloud Storage，沒有新增套件；寫入帶「不存在才建立」的條件，服務帳號也只有新增與讀取的權限。自動測試用 `MemoryStorage`。
- 新增 `app/` 底下的檔案時，`deploy/core-e2e-build-sources.txt` 要同步。
- 2026-11-12 起閱讀器是 `reader-2`、劇情資料是 `lw-story.v2`（各章放在 `chapters`；單一作品就是只有一章，沒有目錄）。多章節作品匯出時只包含已採納的章節，有目錄。
- 同一天稍晚升到 `reader-3`、`lw-story.v3`：人物顏色、陣營、幕名與起承轉合、類型、下集預告，以及敘事／台詞／場景提示三種字體（見「通用的故事原則」）。已經匯出過的檔案不受影響。合集裡只有最後一章顯示下集預告。
- 還沒做的：圖片、互動選項；匯出檔沒有清理或保留期限；舊的故事開場、短篇互動、人物劇場作品不能匯出。

### 多章節作品（2026-11-12，第 2 級）

一部作品可以分批續寫。每一章是一件既有的生成作品；續寫出來的先是草稿，使用者採納之後才成為主線的下一章。續寫時 AI 帶著前面的劇情接著寫，這些內容全部取自已保存的規劃與段落，沒有多一次模型呼叫。

| 規則 | 在哪裡 |
|---|---|
| 多章節作品是 `works` 的一種（`kind='story_series'`），識別碼由第 1 章的作品識別碼以 UUIDv5 推導；每次變動新增一個版本（只增不改） | `story_series.py` 的 `open_series`、`_series_save` |
| 主線只在採納時改變。草稿不論生成中、完成或捨棄，都不影響已定稿的章節與檢查點 | `adopt_series_episode` |
| 草稿只能接在它開始時的進度上；主線已經往前就回 409 `series_base_changed` | 同上 |
| 續寫的作品在 `meta.series` 記下屬於哪一部、接在第幾章後面，在 `meta.continuity` 鎖定當時繼承的內容 | `start_series_episode`（沿用 `roleplay.start_generation`，多了 `prepare`／`after`） |
| 規劃看得到各章大綱與上一章最後 6 段；人物發言時帶著自己前面章節的記憶（最多 12 則）與最後的狀態；上一章結尾只給當時在場的人 | `story_continuity.py`、`roleplay.py` 的兩個 `resolve` |
| 劇情狀態只存在作品裡，不寫回人物、人物設定、我的設定、我的經歷 | — |

補充：

- 檢查點的內容：各章大綱（規劃時模型寫的標題、前提、節拍目標，2026-11-12 起加上那一章使用者寫的場景描述與場景條件）、上一章結尾（說話者、台詞、動作與在場的人）、每位人物最後的狀態與累積的記憶。在這之前開成多章節作品的，已定稿章節的大綱沒有場景，不會回頭補。
- 人物跨章用固定代號辨認（`person:{人物}`、`card:{角色卡}`、`self`），不用每章重新編的陣容代號。
- 提示詞在這一級升到 `roleplay-plan-v4`／`roleplay-segment-v4`：規則和 v3 相同，多一條「延續前面章節」。`story_so_far` 只有續寫的章節才有。現行版本是 v8（見後面的「通用的故事原則」），「延續前面章節」的規則仍在；v2 到 v7 保留給進行中的作品。
- 續寫沿用第 1 章的陣容、風格與演出要求；每一章各自鎖定開始當下最新的正式人物設定。長度與呈現形式可以每一章另外選，表單預設成第 1 章的設定（`GET /api/series/{id}` 的 `output`；2026-11-12 修正，原本固定預設劇本對白）。
- 捨棄草稿就是封存那件作品（既有的 `POST /api/works/{id}/status`）。
- 作品中心多了「多章節作品」這一種；每一章仍然各自列在作品中心。
- 還沒做的：分支（從舊進度另開一條線）、番外與前傳、修改已生成的段落、中途換陣容、用模型整理摘要與未解伏筆、劇情變數；已採納的章節被封存時沒有防護；草稿清單記在多章節作品的內容裡，作品很多時要改成欄位或資料表。

### 人物個性的表現（2026-11-12，提示詞 v5）

使用者看過真實模型生成的作品後指出：人物只是把台詞說出來，看不出個性，也看不出人物之間的差異。`roleplay-plan-v5`／`roleplay-segment-v5` 針對檢視出來的原因修改，輸出欄位與上限沒有變（Schema 與 v4 相同）。

| 原因 | v5 的規則 |
|---|---|
| 規劃把「誰做什麼」寫進節拍（例如「拿起標籤草稿，思索字句」），人物只能照做 | 規劃的 `goal` 只寫情況（發生了什麼、要決定什麼），不寫哪一位人物怎麼想、怎麼說、怎麼做；每個節拍要帶來新的情況；兩位以上時安排會讓差異顯現的情況 |
| 逐段提示只說「依照人格演出」 | 說明人物設定每一欄的用途；動筆前先判斷這個人會注意什麼、想要什麼、會怎麼做；個性從選擇與行為看出來，不讓人物描述自己的性格；有壓力時讓弱點顯現 |
| 口頭禪每一段都出現；每一段都描寫光線 | 口頭禪與設定中引號裡的句子整部作品最多一次，用過的句型與動作不重複；場景提示沒有變化就留空 |
| 人物各說各話 | 有其他人在場時要針對對方說的話或做的事表態，不附和、不模仿對方的語氣 |

補充：

- 沒有改變的規則：規劃只看公開簡介；發言的人只看得到自己的完整設定與自己在場看到的段落。
- 人物的差異主要來自人物設定本身。九欄裡對表現影響最大的是性格、說話方式、行為習慣、動機與弱點；只填背景或每位人物寫得差不多，生成出來就不會有差異。
- 規劃看不到九欄，所以公開簡介（人物的簡介欄）最好寫出這個人的做事方式，規劃才安排得出會顯出差異的情況。
- 提示詞的效果只能用真實模型的結果判斷。`tests/test_persona_expression_prompt.py` 只確認版本、舊版本不變、送出的欄位都有說明、關鍵規則有送出。
- 2026-11-12 真實模型的結果（兩位個性相反的人物、兩章 24 段）：兩人的說話方式、行為習慣、堅持的事都分得出來，會互相回應，口頭禪沒有重複，場景提示大多留空。同一次也看到三個還沒解決的問題：規劃的節拍有時仍然寫出人物的態度（例如「某人認為……」）；第 2 章有一段和第 1 章已經成立的事實矛盾（第 1 章說紋樣沒有依據，第 2 章人物卻說是照榫頭位置推敲的）；同一個節拍裡偶爾有人先回應了還沒發生的事。
- 跨章一致（2026-11-12，提示詞 v6）：各章大綱帶上使用者寫的場景與條件；提示加上「已經成立的事實不能改變、不能替沒有依據的事補上依據」、「依 `beat.position`：第一個發言的人把情況帶出來，之後的人接著往下寫」、「節拍不寫人物的想法、態度或立場」。同一組人物與場景再跑一次，第 2 章沒有再出現和第 1 章相反的說法，也沒有先回應後發生；節拍寫出人物態度的情形還有，時間細節還會前後不一致。只跑了一次。
- 2026-11-12 在使用者的 E2E 帳號用兩位人物生成的第一件短篇：兩人第 2 段就達成共識、第 4 段就把問題解決，後面 6 段都在收尾。節奏的問題還沒有處理：可以在規劃要求「主要的分歧至少維持到倒數第二個節拍、收拾與道別不單獨成為節拍」，在逐段要求「依 `turn.turn_no`／`turn.total` 控制進度，答應之前先說出自己的保留、條件或代價」。兩位人物性情相近、場景沒有壓力時，差異本來就不容易顯出來。
- 還沒做的：沒有自動檢查重複（例如同一句口頭禪出現兩次就重新生成）；沒有「先寫內心打算、再寫台詞」的中間欄位；規劃看不到性格，兩位人物的公開簡介都很短時，情況可能安排得不夠有張力；舊的故事開場、短篇互動、人物劇場沒有套用這些規則。

### 破題、名場面與節奏（2026-11-12，提示詞 v7）

使用者對作品內容的方向：作品要像文章一樣先破題，讓人在開演前就有期待；要用觀眾熟悉的東西來演，可以是歷史名場面照原樣演，也可以把名場面改編成現代、商戰、生活或科幻。熟悉的東西可以省掉解釋，改編帶出驚喜。

| 做法 | 在哪裡 |
|---|---|
| 開場白（破題）：規劃寫的 `premise` 是開演前給觀眾看的，交代誰和誰、為了什麼、輸了失去什麼、最想知道的問題，不寫結局 | `roleplay-plan-v7` 第 15 條；作品頁（`generation.js` 的 `panel`）與匯出檔都顯示在第一段之前 |
| 藍本：場景、劇情起點或演出要求提到觀眾熟悉的名場面時，依它最為人熟知的橋段安排節拍，節拍用「對應〈橋段名稱〉：」開頭；人物保留自己的名字與個性 | `roleplay-plan-v7` 第 16 條、`roleplay-segment-v7` 第 18 條 |
| 名場面範例場景：建立頁「② 場景 → 從範例場景開始」有 5 個「名場面｜」，選了帶入描述，再補上誰站在哪一方 | `app/catalog/scene_presets.v1.json` |
| 節奏：主要的懸念到最後一個節拍才有結果；同意之前先說保留或代價；不安排只有收拾、道別的節拍 | 第 17 條、第 19 條；逐段收到 `beat.total` |

補充：

- 沒有提到藍本時，規劃不會自己套用名場面，但開場白與節奏的規則仍然適用。
- 規劃怎麼知道名場面的內容：靠模型自己的知識，沒有另外的資料。冷門的典故可能被演錯。
- 名場面範例場景只有 5 個，是寫死在目錄檔裡的；「名場面」與「改編方式」不是分開的欄位，要別的組合就自己在場景描述寫「藍本：○○，改編成○○」。
- 2026-11-12 在使用者的 E2E 帳號生成的名場面改編中篇（三位人物，提示詞 v7）看到的問題，都還沒處理：結局沒有回答開場白的問題，藍本最後一個橋段沒有演完；三個人用同一套比喻說話，台詞抽象；名字相近的人物被寫錯（兩個相近的名字混在一起）；場景提示仍然太多；同一個人連續說兩段。
- 可以做的方向（還沒做）：最後一段必須讓開場白的問題有明確答案；台詞要講具體的事，同一個比喻全篇最多一次；規劃不讓同一個人連續發言；輸出後檢查有沒有出現陣容以外的人名；換用較強的模型比較。

### 通用的故事原則（2026-11-12，提示詞 v8）

使用者的要求：規則必須不分題材都成立，不是為了某一種戲劇效果而加。v8 把 v5 到 v7 一條一條往後加的指令整份重寫；前面三個小節（人物個性、跨章一致、破題與名場面）的規則都還在 v8 裡面，寫法不同而已。

| 原則（規劃） | 意思 |
|---|---|
| 類型與承諾 | 先判斷是哪一類作品，兌現那一類觀眾期待的東西（懸疑的線索與揭曉、戀愛的心動與誤會、冒險的關卡與成長、遊戲對局的規則與輸贏、旅行的取捨與難忘片刻……） |
| 一個問題 | 整場圍繞一個觀眾最想知道答案的問題，每個節拍讓答案更近或更難 |
| 起承轉合 | 每個節拍標 `kind`（setup／rise／turn／payoff）；至少一個轉，最後一個是合 |
| 意料之外、情理之中 | 轉折用到的人、物或消息，前面要出現過 |
| 只有他知道的事 | `private_notes`：底牌、秘密、隱藏的身分、沒說出口的心意、準備好的驚喜；只交給本人，到轉或合才揭開 |
| 具體、自己解決 | 每個節拍有看得見的東西或事件；難題由面對它的人解決，不由對方讓步或巧合化解 |
| 結尾 | 回答那個問題；可以完整收尾，也可以帶出更大的問題並寫 `teaser`（下集預告） |

資料與顯示：

- 規劃的新欄位都存在作品內容的 `plan` 裡：`genre`、`sides`、`private_notes`、`beats[].title`、`beats[].kind`、`teaser`。舊作品沒有，畫面與匯出照舊。
- `private_notes` 在作品頁與閱讀版不顯示、不匯出（互動版會帶上，預設收合，見「互動版匯出」）：`GET /api/generation/runs/{id}` 回的 `plan` 已經拿掉它；它只留在作品內容裡（原始的 `GET /api/works/{id}` 看得到），之後互動版可以拿來做「看底牌」。
- 個人、團體、關鍵情節的區別：個人＝依陣容順序的 6 種顏色；團體＝規劃標出的陣營；關鍵情節＝每一幕的幕名與起承轉合，轉折那一幕另有樣式。作品頁在 `generation.js` 與 `characters.css`，匯出檔在 `reader-3`。
- 逐段多收到 `beat.title`、`beat.kind`、`sides`、自己的 `private_note`，以及最後一個節拍才有的 `closing.teaser`。

已知的問題（2026-11-12 在使用者的 E2E 帳號生成的名場面改編中篇，提示詞 v8）：

- 結構性的要求做得到；細緻的要求（同一種小動作不重複、場景提示少寫、不演錯人）`gemini-3.5-flash-lite` 遵守得不穩定。那件作品有一段演錯人（對手說了主角的立場），同一個小道具出現 7 次。
- v8 的規劃沒有照「對應〈橋段名稱〉：」標出藍本的橋段，名場面比 v7 那一件不容易認出來。
- 可以做的方向（還沒做）：場景提示只保留每一幕的第一段（程式處理，不靠模型）；輸出後檢查「說話的人稱呼自己」這類演錯人的跡象並重試；換較強的模型比較；續寫表單用上一章的下集預告當預設場景。

### 互動版匯出（2026-11-12，play-1）

同一件作品可以匯出兩種單檔離線 HTML：閱讀版（`reader-3`）與互動版（`play-1`）。互動版只用已經保存的資料，不呼叫模型。

- API：`POST /api/works/{id}/exports` 的 body 多一個可選的 `player`（`reader`｜`play`）。不帶就是閱讀版；同一個 `request_id` 換另一種會回 409。兩種共用同一個匯出紀錄與版本號；「內容相同就回舊版本」是各自和同一種播放器最新的一筆比。互動版的檔名多「（互動版）」。
- 資料：`lw-play.v1` 是 `lw-story.v3` 的超集。每段多 `state`（那一段之後這位人物的情緒、立場、目標；取自段落保存的狀態）與 `who`；每章多 `secrets`（規劃裡的 `private_notes`）。閱讀版不含這些，輸出和加入互動版之前逐位元相同。
- 播放器（`app/export_player/play-1.css`、`play-1.js`）：逐段揭開、「真心話」開關、人物篩選、讀完才出現的結尾卡（下集預告、看底牌、你站哪一邊、從頭再看）。漸進增強：沒有 JS 時整篇可讀，底牌用 `<details>` 收合。偏好記在 localStorage（`lw-play-prefs`，陣營選擇是 `lw-play-pick:` 加作品標題）。
- 底牌會寫進互動版的檔案裡（預設收合）。拿到檔案的人看原始碼就看得到；這是作品的一部分，不是人物設定。
- 還沒做的：需要模型多生成的互動（每一幕結尾的選擇題與走錯的結局、張力數值）；閱讀進度不跨重新整理保存；作品頁的「上次匯出」沒有標是哪一種；沒有在 8030 的 Chrome 測試裡涵蓋「下載互動版」。App 內的瀏覽器面板按下載不會存檔，要用自己的瀏覽器按。

### 互動層（2026-11-12，interactive-layer-v1）與 play-2

互動版從閱讀輔助改成有東西可猜、選擇會改變結局。上一小節的 play-1 已經被 play-2 取代（`lw-play.v2`）；API 的 `player: play` 不變。

| 項目 | 說明 |
|---|---|
| 互動層 | 作品完成後多呼叫一次模型產生，存進作品內容的 `interactive`（`lw-interactive.v1`）：`decision`（`after_beat`、`actor`、`question`、三個 `options`）、`clues`、`epilogues`、`question` |
| 產生時機 | 作品頁按「下載互動版」時先 `POST /api/works/{id}/interactive`；已經有就不再呼叫。回應只有數量，不含內容 |
| 資料隔離 | 送給模型的只有作品本身與底牌，不含人物設定；`roleplay_detail` 只回 `interactive: {available, has_decision}` |
| 整理 | `tidy_layer`：選項必須剛好三個、剛好一個 `true`；線索的詞必須是原文一字不差的子字串、在抉擇點以前、指向有底牌的人；寫錯的丟掉 |
| 抉擇點 | 程式決定：最後一個後面還有節拍的 `turn` 之後；沒有就是倒數第二個節拍之後 |
| 播放器 | 選視角、限次偷看別人的真心話、點線索詞、抉擇卡、三個結局與重選、結局計數、選邊後的番外與提問 |

已知的問題（2026-11-12 兩件真實作品）：

- 線索兩次都是 0 則，「找到線索才能選真結局」沒有發揮。可以做的：指令改成有底牌時盡量為每個底牌找一則；比對放寬（忽略標點與空白，取那一段裡最接近的子字串）；記下模型給了幾則、留下幾則。
- 抉擇點固定在轉折之後，有時真結局的做法讀者已經看過。可以做的：讓模型在程式限定的範圍內選一個段落當抉擇點（主角做出關鍵動作之前）。
- 互動層產生一次就固定，沒有重做的入口；要套用新的規則得加「重新準備互動內容」。
- 同一個 `request_id` 失敗後重送只會回同一個錯誤，前端每次按都換新的代號。
- `GET /api/works/{id}` 回整份作品內容（含底牌與互動層），前端沒有用它顯示，但直接呼叫看得到。
- 真實的互動版檔案沒有在瀏覽器裡實際點過（面板按下載不存檔）；8030 的 Chrome 測試沒有涵蓋下載互動版。

### 回合制互動作品（2026-11-12，第 1 期：行程題材）

使用者定案的產品方向：最重要的仍是 AI 角色扮演。使用者在自己的回合做選擇，其他角色各自依個性反應；每位角色有一個數值，每個選項讓不同角色的數值各自升降，數值決定多結局。互動與視覺效果是加分。題材不限（旅遊、登山、商城購物、食材採購、劇情多結局……），引擎共用，只換節點與資源。成品是可離線、可傳給親友玩的單一 HTML，也能在站內直接玩。

| 項目 | 說明 | 在哪裡 |
|---|---|---|
