# Life World｜Goal Detail / Dashboard 頁面重構——產品與工程交接規格

**文件 ID：LW-GOAL-DETAIL-002｜版本：v0.2 審查草案｜日期：2026-11-03**<br>
**適用範圍：**既有「目標」分頁中的單一目標詳情；不新增第五個主分頁。<br>
**審查依據：**使用者 2026-11-03 上傳之頁面截圖；GitHub 已核對 `app/static/app.js` 之 `goalCard()`、`worldView()`、`goalProgress()`，與 `app/static/goals.js` 之 `list()`、`detail()`，以及既有 `docs/API.md`／封測 v1.1 決策。**本文件為待核准的重構方案，非已實作行為。**

## 1. 一句話決策

**順序固定為「Goal（目標本身）→ 目標總覽（現在進展與下一步）→ 三項習慣明細 → 最近七天趨勢 → 日期與佐證／回顧明細」。** 上方提供足夠的判斷資訊，但不得把所有細節平鋪在第一屏。Goal Header 不應顯示冗長的各習慣內容；細節總覽也不等於把所有資訊堆進一張巨大卡片。

### 1.1 使用者問題
- 目前畫面在「成為海賊王／超帥超厲害／2026-10-29～2028-01-01」下，直接逐一列出「每天健身：369 個已安排日」、「認識三個朋友成為船員：62 個已安排日」及每項的「記錄」按鈕。
- 使用者看不到「已確認投入」與「已安排」的清楚區別；長目標需要大量滑動，主要操作分散。
- 目前呈現對數據核對有用，但無法在數秒內回答：**我的目標是什麼、今天能做什麼、真正累積了什麼、下一步去哪裡？**

### 1.2 既有規則，不得破壞
1. 固定四主分頁「世界／目標／紀錄／關係」，現有版本單一進行中目標，三項習慣；歷史目標仍可看。
2. `active`、`awaiting_review`、`needs_setup`、`completed`、`ended` 生命週期保持現有 API 語意。
3. 排程是**計畫**，不是完成；習慣的已確認數量才可計入投入。最終目標成果須獨立人工確認；習慣達標不代表成果完成。
4. 封測 v1.1 不展示積分、養分、兌換或懲罰機制。正式 App 既有帳本不因 UI 變動而刪除或重算。
5. 日期按目標固定 `schedule_timezone`，保留既有用量版本、生效日與期外貢獻採計規則。

## 3. 文案與數字語意（必要）

| 資訊 | 正確標籤 | 禁止作法 |
|---|---|---|
| Goal title | 目標名稱（例：成為海賊王） | 將成果描述當成另一個同等層級標題 |
| Outcome | 想達成的成果（例：超帥超厲害） | 將文字誤作已達成 |
| Scheduled days | 已安排 369 天 | 用「已做 369 次」或當作完成率 |
| Action target | 目標投入 X 次／小時，依現行用量版本及排程衍生 | 跨不同單位直接相加 |
| Action progress | 已確認投入 Y 次／小時，來自後端實際確認量 | 依排程或勾選推估完成 |
| Goal completion | `completed` 狀態及人工確認完成日期 | 以習慣百分比自動判定達成 |
| Seven-day count | 最近七天已採計經歷，按發生日且同 ID 只計一次 | 把未確認、待處理、未採計或模擬事件一併計入 |
| Zero data | 尚無已採計經歷／今天沒有安排 | 顯示紅色「失敗／缺席／沒努力」 |

### 3.1 禁止先做「整體目標完成 40%」
三個習慣可能有不同單位及目標用量，`action.progress / action.target` 是**各習慣自己的比例**。本次沒有經核准的跨習慣權重或最終成果完成度算法；Goal Hero 不顯示拼湊的百分比。若未來需要「綜合進度」，須另開產品決策、定義公式、含零分母與調整排程後的處理。

## 4. 資料讀取／ViewModel 候選契約

下列型別是**頁面層 ViewModel 建議**，不是已存在 API／Migration：

```ts
interface GoalDetailVM {
  goal: {
    id: string; title: string; outcome: string;
    status: 'active'|'awaiting_review'|'needs_setup'|'completed'|'ended';
    startDate: string; deadline: string|null; scheduleTimezone: string;
  };
  habits: Array<{
    actionId: string; title: string; unit: string;
    confirmedQuantity: string; targetQuantity: string|null;
    scheduledDayCount: number; nextScheduledDate: string|null;
    scheduleDates: string[]|null;
  }>;
  today: { isoDate: string; scheduledActionIds: string[] };
  overview: { appliedExperienceCount7d: number|null;
              pendingContributionCount: number|null;
              recentWindowStart: string; recentWindowEnd: string; };
  week: Array<{ localDate: string; distinctAppliedExperienceIds: string[] }> | null;
  dataStatus: 'ready'|'partial'|'loading'|'error';
}
```

- **資料來源優先順序**：從現有 `GET /api/goals/{id}`、行動 `actions[].progress / target / unit / dates / quantity_versions`、`pending_contributions`、現有 `/state` 及授權經歷來源聚合；不得在 UI 隨機產生 KPI。
- **待確認契約**：目前 API 是否足以直接判定「最近七天有被採計的 distinct experience IDs」。若不足，先由工程列出最小的受權限保護讀取契約，再決定 server-side aggregation；不得用「確認經歷總筆數」偽裝「已採計經歷」。
- 七日範圍包含目標時區今天與前六日；`occurred_at` 換算目標時區日期；相同經歷貢獻多個習慣只算一筆。撤回／未採計／待核對不計入。
- 既有資料不提供欄位時標示「暫無統計」，而非呈現假 0。`scheduledDayCount` 與 `targetQuantity` 不做相互替代。
- 若狀態 `awaiting_review`、`needs_setup`、`ended` 或 `completed`，CTA、日期編輯及待採計操作依後端授權切換。

## 5. 互動與例外狀態

- **導航**：維持現有四主分頁；`#goals` 為列表／目標花園，`#goal/{id}` 為目標詳情。從世界首頁點目標卡進詳情，返回仍能找回原位置。
- **記錄 CTA**：Goal Hero 的「記錄經歷」帶入目標；Habit 卡「記錄此習慣」再預選 action。預選僅設定草稿上下文，不視為已完成；沒有可用活動選項時提供文字紀錄退路，不建立假貢獻。
- **日期編輯**：沿用現有 GoalsUI 排程；只修改允許的未來安排，期望量生效日期與 `expected_revision` 仍由後端驗證。發生 409 衝突時提示讀取最新版後重新核對。
- **加載**：Hero／Habit 卡可先顯示骨架，但不得把載入中的缺值顯示為「0 次」。
- **空白**：無今日日程顯示「今天沒有安排，依自己的節奏就好」；無已採計紀錄顯示中性說明。
- **錯誤**：資料查詢失敗保留已成功的部分，對未載區塊顯示可重試；不可遺失正在編輯的草稿。
- **逾期／結束**：保留目標與已確認投入的歷史；待回顧按既有交易逐筆處理，已結束目標不可從 Dashboard 偷偷重新打開。
- **無障礙**：按鈕有可見名稱、鍵盤焦點、讀屏標籤；圖表必有等價數據表／列表，不以色彩單獨表達。

## 6. 實作邊界與交接

- 前端先調整 `app/static/goals.js` 的 `detail()` 區塊順序及新 ViewModel／子元件；與 `app/static/app.js` 既有 `goalCard`／`goalProgress` 重用，不新增 React 或另一套全域樣式。
- 繼承原 API 的目標／習慣／待處理貢獻與成果確認交易。若需新增每日聚合讀取契約，先審 API、權限與計數口徑，不直接動 Schema。
- 不變更 `app/migrations`、正式獎勵、人物劇場 Session 或人物資料；不把展示站 React UI Kit 視為正式 App 已接入。
- 開發人員需先記錄來源 commit、現有 dirty worktree、預期改動檔案及與既有 Dashboard v0.1 文件的差異；使用團隊核准設計 tokens，保留 Quiet／Reduced Motion。
