## 1. 問題、目標與不做事項

**現況：**目標詳情中三個習慣的 `<details>` 展開後，`app/static/goals.js` 直接將 `a.dates` 以 `join()` 列出。長期排程（例如 369 個已安排日）造成大量文字、難以定位今天／下次、看不出當日用量，也無法清楚區分「計畫」與「真實投入」。

**目標：**改成 **習慣摘要（預設收合）→ 月曆（逐月查看）→ 點選日期查看當日預期用量及已確認投入（若有授權資料）**。使用者可在 320px 手機上快速找出下次安排，不必閱讀幾百個日期；查看不會修改排程。

**不做：**不建立第五主分頁；不改三習慣／單一進行中目標／目標生命週期；不新增獎勵、Lumi 動畫、綜合完成率；不在 UI 自行認定已完成、不自動建立經歷或任務；不要求新資料表、React 重寫或新圖表套件；不因檢視月曆而發送寫入 API。

## 2. 版面與操作流程

### 2.1 習慣摘要（預設收合）

由 `HabitSummaryCard` 提供：

- 習慣名稱，例如「每天健身」。
- **已確認投入** `progress + unit`（若已知）；**已安排** `N 天`；**下次安排** `MM/DD（星期）` 或「本次目標期間已無後續安排」。三者不同，不得互相換算。
- 主要行動：`記錄此習慣`。只有後端允許的目標／行動才提供可用入口；進入經歷表單須預選 `goalId + actionId`，仍要完成原有人工確認後才計入投入。
- 次要控制：`查看日期與用量`（`aria-expanded=false`）；展開後改為 `收合日期與用量`。
- 同張卡內容不要重複列出 369 個 ISO 日期；也不得用「已安排 369 天」取代「已確認 369 次」。

### 2.2 月曆檢視（展開後）

- 顯示 `YYYY 年 M 月`，左／右分別為上一月、下一月；不可瀏覽目標 `start_date` 至 `deadline` 以外的月份（邊界按月比較）。月曆採**週一至週日**欄頭。
- 初次展開的月份：進行中目標以**目標固定時區的今天**所在月份為優先，超出目標期間時夾到最近的有效邊界月份；已完成／已結束目標優先顯示最後一個有安排的月份，若無則為起始月份。此選擇是**建議規則，需產品核准**。
- 只渲染可視月份最多 31 個日期格及必要的空白補位；切月僅更新本地檢視狀態與當月資料，不累積長 DOM。
- **有安排**：日期格以中性標記（例如小點）顯示；**無安排**：一般日期樣式。若「已確認投入」逐日資料**確實可得**，可疊加另一個明確標記；不可僅靠顏色傳達資訊。
- **日期選取**：檢視模式下，目標期間內無安排的日期也可查看「當日未安排」，但不會產生編輯。目標期間外日期不可選取／不得提供用量值。選取日期不提交 API、不觸發資料變更。
- 切月行為不建立一筆新的整頁瀏覽器歷史；返回目標詳情後恢復上次月份、選日、展開狀態及合理捲動位置，符合 Navigation Contract。

### 2.3 單日明細

點選日期後，在月曆下方顯示固定位置的 `DayScheduleDetail`：

1. 完整日期及星期，例如「2026/11/03（二）」。
2. 排程狀態：`已安排`／`未安排`／`目標期間外`（期間外不應可選）。
3. **原訂預期量**：後端授權資料可得時顯示，例如「1 次」。若該日未安排，顯示「這天沒有安排這項習慣」，不顯示假的 0 次完成。
4. **已確認投入**：**只在有可信的該日經歷貢獻資料時**顯示數字／單位與可回看來源的入口。若現有 API 只有習慣累積值、沒有每日資料，明示「當日已確認投入暫無逐日統計」，**不能顯示 0**。
5. 若可執行：`記錄這次投入` → 既有經歷輸入流程；先核對再保存。**查看月曆及點選日期不等於完成、未完成或產生獎勵。**

### 2.4 查看與編輯的邊界

`查看日期與用量` 是唯讀。使用者要改未來安排時，必須另按 `調整未來安排` 進入現有 Goal Review／Schedule 編輯流程；不允許點一下日期就更改排程。編輯提交沿用 `expected_revision`、`expected_effective_from` 及後端核對，不改歷史投入，409 衝突要提供載入最新版再核對。

## 3. 資料契約：現有來源與待補欄位

| 顯示欄位 | 現有或候選來源 | 規則及缺少資料時的處理 |
|---|---|---|
| `goalId`／`actionId` | 現有 `GET /api/goals/{id}` 及 `actions[]` | 必須是後端認可的目標／習慣；不信任 URL 任意 ID |
| `startDate`／`deadline` | 既有目標資料 | ISO 日期含首尾；只作可見月份與日期邊界 |
| `scheduleTimezone`／`today` | `GET /api/goals/{id}` | 使用目標固定 IANA 時區；不從裝置時區猜測日期 |
| `scheduledDates[]` | `actions[].dates`，優先參考授權後端月曆 | 已安排日集合；對舊版 `dates=null` 不自行展開假日期 |
| `plannedQuantityByDate` | `GET /api/goals/{id}/calendar?start=…&end=…` 的 `planned_quantities` 等欄位（實際 response shape 須工程確認） | 優先由後端計算該日有效用量版本；不可直接用今天的 `per_occurrence` 填滿整段歷史 |
| `actionProgress`／`actionTarget`／`unit` | 既有 action 累積資料 | 供習慣摘要使用，不等同某日完成量 |
| `dailyConfirmedQuantity`／`sourceExperienceIds` | **待核對：現有 API 未確認可提供完整逐日值** | 未獲資料則標「暫無逐日統計」，不得衍生假 0；如需新增只讀 API，另提最小契約與權限審查 |
| `status`／`allowedActions` | 目標公開生命週期及後端允許操作 | `active`／`awaiting_review`／`needs_setup`／`completed`／`ended` 分別決定唯讀、核對與 CTA |

**請工程先做資料能力清點。** 已知現有 `/api/goals/{id}/calendar` 按月查詢，文件限制單次日期區間最多 367 天；本功能一次只請求單一月份（最多 31 天）。正式 response 的 `planned_quantities` 是按 action ID 對應量值，實作前須確認實際物件路徑與舊版相容。若不足以辨識單日是否有已確認投入，**先交付排程月曆**，每日已確認投入標籤列為待接功能，不強制為此新增 DB migration。

### 3.1 前端 ViewModel（建議，非現有 API）

```ts
interface HabitScheduleMonthVM {
  ownerScope: string;          // 前端路由 cache 範圍，絕不提交成為 owner 身分
  goalId: string;
  actionId: string;
  month: string;               // YYYY-MM
  scheduleTimezone: string;
  startDate: string;           // YYYY-MM-DD
  deadline: string;            // YYYY-MM-DD
  days: Array<{
    date: string;
    withinGoal: boolean;
    scheduled: boolean;
    plannedQuantity: string | null; // null = 未安排或資料缺失，需搭配狀態判讀
    unit: string;
    confirmedQuantity: string | null; // null = 無逐日可信資料，不等於 0
    confirmedStatus: 'known' | 'unavailable';
    sourceExperienceIds?: string[]; // 只有後端核准授權來源時提供
  }>;
}
```

快取鍵必須包含目前登入使用者範圍、`goalId`、`actionId`、月份及必要資料版本；切換帳號後清空。不能將經歷全文／敏感檔案放在 `history.state`。

## 5. 交互、返回與異常狀態

| 情境 | 必須行為 |
|---|---|
| 首次展開 | 顯示有效月份；若已載入則立即可讀，尚未載入顯示 loading，不假畫資料 |
| 切換上／下月 | 若失敗保留原已讀資料及選取狀態，顯示「無法載入月份／重試」；過期請求不可蓋新月份 |
| 切換習慣／目標 | 每張卡的月份／選日獨立；不串用其他習慣資料 |
| 返回上層再回目標 | 恢復展開、月份、選日、合理捲動；單純切月不新增 History Entry |
| 重新整理／深連結 | 由合法 URL 與 API 重建；可退回預設月份，不能依賴 JS 記憶體才能看到畫面 |
| 已結束／已完成 | 可唯讀回看排程，不能以查看動作開啟新採計寫入 |
| 無安排 | 顯示「這個月尚未安排此習慣」，不暗示失敗或未努力 |
| 期間外／舊資料 `dates=null` | 不猜測數據；顯示可解釋的唯讀退路，必要時引導既有設定補齊流程 |
| 已確認資料未供應 | 預期量照常展示；實際投入顯示「暫無逐日統計」，不補成 0 |
| 失去授權／跨帳號 | 404／403 時不渲染私人來源，清除該帳號檢視快取 |
| 變更排程造成 409 | 不在唯讀月曆消化寫入；由既有編輯流程載入最新版並再核對 |
