## 1. 使用者問題與成功條件

**使用者需求：** 為現實中的困難對話、會議或人際情境預先演練。不是每個人都會順從、回答、接納玩家的提議；使用者需要看到不同合理反應，保有自主判斷，而非被 AI 給出「最佳答案」。

**成功條件（產品驗證，尚未實測）：**

1. 新使用者知道主要動作是「建立我的情境」，可以不讀教學就啟動一次合法且完整的劇場。
2. 能清楚辨認角色在對誰說話，且角色可能沉默、暫緩、迴避或不接受使用者要求。
3. 玩家能自由發言、繼續旁聽、暫停問 Lumi、隨時退出，而不是被劇場連續訊息鎖住。
4. 結束後知道已說明的立場、未解決問題與**可能影響討論的片段**；不把 AI 推論當成已證明的因果。
5. 模擬紀錄不能成為真人觀測／使用者長期人格資料；失敗與限制不會冒充角色行為。

### 2.1 建立器最低輸入與驗證

| 欄位 | 規則 | 例外 |
|---|---|---|
| 情境描述 | 自然語言自由輸入；不以字數作為唯一門檻 | 內容缺乏可理解情境時只問一個必要問題或提示範例 |
| 人物 | **v1.1 自訂僅能勾選「我的人物」**；示範情境使用其獨立示範角色 | 未建人物提供「先體驗示範情境」或「前往建立人物」；首輪不提供臨時角色 |

**首輪人物來源限制 [PM 決策]：** `saved_person` 用於自訂情境；`demo_persona` 只用於獨立示範情境。`temporary_persona` 與混用不同類型人物為未來擴充，**不列入 v1.1**。

- 情境輸入：「你想模擬什麼情境？」
- 選人物：「選擇這場對話會出現的人物」
- 目標：「這次你希望練習什麼？」
- 模擬提醒：「這是根據可用資料與情境假設進行的模擬，不代表真人一定會這樣反應。」
- 進階入口：「進階真實模擬劇場｜規劃中：人物反應時間、對話打斷與更複雜的自主互動。」

## 3. 劇場共用互動規則

### 3.1 操作控制權與情境發言權必須分離 [PM 決策]

玩家始終可以**暫停、輸入、嘗試插話、繼續旁聽、開啟 Lumi、結束**。但在模擬情境中，其他人物可以沒有立即回應玩家、維持相反立場、繼續彼此對話。這是練習的一部分，不應由 UI 保證玩家每次獲得注意或同意。

**v1.1 的「嘗試插話」**可作為下一個玩家輸入／行動，由角色在下一段生成中接受、忽略或暫緩；**不等於**能在已開始串流的單句中做真正的即時打斷。後者屬正式 V1 的進階能力。

### 3.2 1v1

- 同一 Session 聚焦一個目標或事件；較多人可有更長的往返，但不得無限延長。
- 不硬套「開場／協商／達成協議」劇本；談心、道歉、職場練習可有不同的結束條件。
- 系統可在已釐清條件、出現重複、角色不願繼續或達到範圍時提出自然收尾；玩家也能主動結束。
- 請求上限與對話長度依 `mode` 設定，**具體數值待工程評估及產品確認**。

### 3.3 多人：先 C1，保留 C2／C3 架構

- **C1 [v1.1]：** 一次由後端控制的生成節點產生**有限的 1–3 段角色回應（候選值）**，可以是 A 對 B 發言；這一段結束後不自行無限制啟動下一次模型請求，使用者可發言／旁聽／暫停／結束。
- **C2 [後續]：** 系統依情境允許有限多段自主推進，必須有明確步數／時間／預算及可中斷策略；本次不視為已交付功能。
- **C3 [理想能力]：** 人物能在一場有限 Session 內更自然地改變發言焦點、打斷、離場、互相影響，維持內在狀態一致；不代表無限執行 Agent。
- 不要求每輪所有角色發言；可有角色沉默、不表態、被忽略。要呈現 **「誰 → 對誰」**，不用好感度數字替代具體言行。

### 3.4 Lumi

- 由使用者主動點選暫停，再以私人面板提出一個可能的澄清問題、介入策略或不同說法。
- Lumi 的建議不會被其他劇場人物得知，也不能更新真人的記憶或角色已說出口的內容。
- Lumi 額外呼叫模型也受 Session 統一限制；無可用配額時顯示可理解狀態，不暗自扣取其他場次資源。

## 4. Behavior Engine v0.1：行為集合與限制

**原則 [PM 決策]：角色必須維持本場的 `stance`（立場）、`objective`（目的）、`known_facts`（已知資訊／未知界線）、`constraints`（限制）。** 角色不能只為討好玩家而無理由轉向，也不能為「更真實」而隨機冒犯使用者。

| 行為代碼 | v1.1 範圍 | 最低可觀察表現 |
|---|---|---|
| `ANSWER` | 必要 | 回答已知或明示假設的問題；未知則不能虛構。 |
| `ASK_BACK` | 必要 | 角色反問或要求澄清，且與當前問題相關。 |
| `SILENCE` | 必要 | 明確產生「未回應」事件，而非顯示空白或 API loading。 |
| `DEFER` | 必要 | 未承諾事項留在本場未解議題，後續不能遺忘。 |
| `CLOSING` | 必要 | 可自然結束或保留分歧；不強迫和解。 |
| `EVADE` | 必要 | 角色轉移焦點、含糊帶過；原問題仍標示未被回答。 |
| `MONOLOGUE` | 必要 | 角色一次生成多個短段落展示，仍可停止播放與退出。 |
| `LEAVE` | 延後 | 個別人物離席後在場集合改變，不等同結束整場。 |
| `INTERRUPT` | 延後 | 真正即時打斷／搶話及連續發言仲裁。 |

**工程策略 [建議]：** `Behavior Engine` 先定可用動作與已知限制，`Conversation Director` 協調發言角色，`LLM Gateway` 只負責需要語言的文字；固定規則可直接處理沉默或結束，避免每個人物每次都獨立呼叫模型。須允許不確定和分支，不能把一次觀測量化為精確人格機率。

### 4.1 假想標籤與情境來源 [PM 決策]

| 資料身分 | 範例 | 劇場如何使用 |
|---|---|---|
| 已確認觀測／使用者轉述 | 「上次會議他要求先看預算」 | 作為有來源的記錄，仍不能當成客觀人格定律。 |
| 待確認人物理解 | 「此人在預算議題上可能較謹慎」 | 可在允許的情境作候選參考，標記為未定。 |
| **劇場假想標籤** | 「為本場假設角色優先考量時程」 | 只當作模擬條件，不寫入真實人物卡。 |

先將三者分流，再決定參與模擬的相對權重。權重數值、如何調整與校準方式由工程及產品另行評估，**本版不制定人格機率分數**。即使是為自訂真人情境增加假設，也不能聲稱該真人「確實具有」這個標籤。

## 5. 回應時間、沉默與未開放的進階模擬

**v1.1 [PM 決策]：不開發完整時間反應系統。**

- 模型處理等待（loading）、角色表演沉默（`SILENCE`）與情境內時間（會議經過多久）是不同概念。
- 角色沉默可立即呈現「對方暫時沒有回應」，再讓使用者選擇等待、澄清、再次發言或結束；不強迫真實等待 30 秒。
- 短暫視覺停頓是 UX 動畫，不代表已測得真人回覆時間。須支援減少動態效果。
- 進階版本才加入反應時間規則、動態議程／倒數及真實打斷；首輪 UI 僅顯示「規劃中」，不做可點擊的失效操作。

## 6. Session 邊界、資源限制與狀態

### 6.1 Session 狀態 [工程契約候選]

`DRAFT → READY → RUNNING → CLOSING → COMPLETED`；另允許 `CANCELLED`、`FAILED`、`EXHAUSTED`。同一 Session 不能有兩個互相競爭的回合生成；重試不能創造兩筆相同玩家行動。

### 6.2 每場硬性限制 [必須有；數值待核准]

| 機制 | 最低要求 |
|---|---|
| `max_model_calls` | 開場、每輪、旁聽後續生成、Lumi、回顧及重試共用總額。 |
| `max_input_tokens` | 控制重複帶入人物歷史造成的上下文膨脹。 |
| `max_output_tokens` | 限制單次及整場文字生成上限，避免長篇輸出失控。 |
| `max_session_cost` | 呼叫前預估並保留餘額；避免以用後帳單當唯一保護。 |
| `max_player_actions` | 依 1v1／多人配置，對使用者以「本場範圍」說明，不暴露 Token 細節。 |
| `retry_limit` | 不重試政策拒絕；技術性重試有次數上限與冪等檢查。 |

**資源耗盡時：** 不再自行呼叫模型；保留已完成對話，顯示本場已達範圍，使用已保存資訊或規則模板進行收尾，不能假裝人物「生氣不說話」。

### 6.3 必須分開的結果代碼

| Code | 意義 | UX 下一步 |
|---|---|---|
| `CHARACTER_SILENCE` | 人物依情境保持沉默 | 等待、澄清、再問、結束 |
| `CHARACTER_DEFERRED` | 人物暫緩表態 | 查看未解議題、繼續詢問 |
| `PROVIDER_REFUSAL` | 模型無法生成該內容 | 簡要說明並可調整情境或結束 |
| `PROVIDER_ERROR` | 網路或服務失敗 | 保留輸入，有限重試或可用回顧 |
| `BUDGET_EXHAUSTED` | 場次資源上限已達 | 明確收尾，查看歷史 |
| `USER_ENDED` | 玩家主動結束 | 依可用資料回顧 |
| `SCENE_CLOSED` | 情境自然收尾 | 顯示各方結果與未知事項 |

## 7. 文字、錄音轉文字與無障礙

- 文字始終可用；錄音須是使用者主動啟動，介面顯示錄音中與停止控制。
- 轉錄完成後可檢查／修改，確認後作為當次玩家發言送出；轉錄失敗不應丟失草稿或阻擋文字輸入。
- 錄音不是即時語音通話；不提供持續監聽，也不為沉默自動開麥克風。
- 對話的說話者／說話對象以文字與可讀標記顯示，不只靠顏色。字幕／長文可收合；不鎖住使用者暫停與結束操作。

## 8. Lumi 回顧、自我紀錄與資料使用 UX

### 8.1 結束回顧最低內容

1. **這場發生什麼事**：依實際生成與玩家輸入彙整，不虛構其他幕後動機。
2. **各角色明確表達的立場**：不能擴大成真人長期個性結論。
3. **可能影響討論的片段**：使用機率性／條件式語言，不宣稱確定因果。
4. **未解問題與下一次可嘗試的做法**：包含未獲共識及沉默等自然結局。
5. **再練一次**：複製情境啟動新 Session；不繼承虛構已達成承諾。

### 8.2 D12 首輪儲存策略 [PM 決策]

- 劇場**只保存本場對話、行為事件及回顧**；提供本場歷史查看及可用的刪除／管理入口。
- 玩家在劇場選擇沉默、嘗試插話或退出，**不得自動寫入長期使用者觀測、人格標籤或 Lumi 個人偏好**。
- 若提供「我的心得」輸入，先只附屬於本場 Session，不上升到 Self Insight；首輪也可以不做此輸入欄。
- 劇場畫面**不顯示「系統正在記錄／觀測你」的持續提示**；資料使用概要集中在註冊與帳號／隱私設定的適當位置。
- v1.1 的保存目的為本場運作、回顧與紀錄管理；**不執行模型微調或使用本場私人內容訓練通用模型**。若未來擴充訓練用途，另設明確可控的使用選項，不將一般服務勾選無限制擴張。

## 9. 資料隔離與接口草案（不代表已存在實體）

### 9.1 必要領域

| 領域 | 資料 | 寫入與引用限制 |
|---|---|---|
| 人物觀測 `Person Insight` | 真實來源、使用者轉述、人工審閱、版本 | 劇場可依權限唯讀引用；不得由模擬服務回寫。 |
| 劇場 `Simulation` | Scenario、Session、Participants、Events、Recap、Usage | 虛構台詞／事件只能留在劇場領域。 |
| 使用者本人 `Self Insight` | 真實自述、已確認的偏好／反思 | 劇場中的行為不得自動生成永久自我標籤。 |

### 9.2 概念契約 [工程建議]

| 概念實體 | 最低欄位／責任 |
|---|---|
| `scenario` | `owner`, `scenario_text`, `goal`, `source_type`, `status` |
| `simulation_session` | `owner`, `scenario_id`, `mode`, `status`, `policy_version`, `started_at`, `ended_at` |
| `participant` | `session_id`, `participant_id`, `person_source_type`, `source_person_id?`, `source_revision?`, `stance`, `objective`, `known_facts`, `constraints`, `presence` |
| `simulation_event` | `session_id`, `sequence`, `actor`, `recipients`, `action_kind`, `content?`, `source_kind=simulation`, `created_at` |
| `scene_state` | `open_issues`, `scene_focus`, `progress`, `turn_owner`, `closing_reason?` |
| `session_usage` | `feature_key`, `request_key`, `model`, `input_tokens`, `output_tokens`, `result_code`, `usage_amount` |
| `simulation_recap` | `summary`, `expressed_stances`, `possible_influences`, `unresolved_issues`, `next_practice` |

這些是抽象名稱，**不得直接當成正式 PostgreSQL 表名**。實際設計應先與 GitHub 最新 `persons`、`observations`、`insight_claims`、`simulation_sessions`、API/OpenAPI 及 migration 比對；必要時採新增關聯表或相容遷移，不直接覆寫既有資料。

### 9.3 不可變條件

- 所有 Session、人物來源、劇場事件均依目前帳號授權存取，拒絕跨使用者資料讀寫。
- 劇場寫入服務不具備直接建立或更新真人正式 `observations` 的權限；跨域更新只能由獨立的真實經歷確認流程觸發。
- `source_kind=simulation` 不能轉型成觀測的事實來源；本場回顧、快取、向量檢索與摘要重建也不得使之滲入人物卡。
- 人物原始觀測撤回／失效後，新開劇場不可引用失效版本；既有紀錄是否保留應遵守既定的資料管理策略。
- 模擬使用的假想標籤／候選理解必須保留來源類型，不得透過一個混合權重欄位掩蓋來源不同。

## 10. 工程實作切片與依賴

| 切片 | 本版要求 | 主要依賴 |
|---|---|---|
| E1 情境建立 | 自訂輸入、我的人物、示範分區、目的及確認 | UX、權限、人物列表 API |
| E2 Session 核心 | 1v1／多人、參與者與來源版本、狀態、冪等 | 後端契約、DB migration |
| E3 Behavior v0.1 | A＋迴避／長篇、角色四項狀態、結束條件 | 事件類型、Prompt／Schema、狀態機 |
| E4 多人 C1 | 單次有限角色間交流、speaker→recipient、玩家選擇旁聽或介入 | Conversation Director、前端訊息呈現 |
| E5 文字／ASR | 文字輸入、主動錄音、轉錄可編修、送出 | 音訊處理、權限、失敗狀態 |
| E6 Lumi／回顧 | 私人求助、情境回顧、可見的歷史紀錄 | Session 讀取、回顧生成或模板 |

## 11. 驗收案例（待執行，不代表通過）

| ID | 情境 | 預期驗收結果 |
|---|---|---|
| AT-01 | 劇場首頁 | 首要 CTA 是「建立我的情境」；示範為次要入口。 |
| AT-02 | 未建任何人物 | 引導建立人物或使用獨立示範；不提供不在範圍內的臨時人物。 |
| AT-03 | 自訂只選 1 人／選多人 | 共用 Builder，建立不同 mode 的 Session。 |
| AT-04 | 情境簡短但可理解 | 可以繼續；缺關鍵條件才要求一項補充，不以固定字數阻擋。 |
| AT-05 | 真人資料不足 | 明示劇場假設，不新增虛構真人歷史。 |
| AT-06 | 角色維持相反立場 | 使用者重複要求時不無理由同意；新資訊可導致合理修正。 |
| AT-07 | 角色沉默 | 產生 `CHARACTER_SILENCE`，玩家仍可等待／澄清／結束。 |
| AT-08 | 角色暫緩 | 後續輪次保留未解問題，不憑空轉成已承諾。 |
| AT-09 | 角色迴避 | 原問題仍保持未解，不把不回答解讀成特定心理動機。 |
| AT-10 | 長篇發言 | 一次生成有限段落；玩家可停止顯示／離開。 |
| AT-11 | 多人 C1 | 存在 A 對 B 發言；生成停止後玩家可發言／繼續旁聽；不無限自動呼叫。 |
| AT-12 | Lumi 私人求助 | 暫停後返回同 Session；私人建議未進入 NPC 可見內容。 |
| AT-13 | 語音轉錄失敗 | 使用者可以重試或改文字，且草稿未遺失。 |
| AT-14 | 模型拒絕／服務故障 | 呈現獨立錯誤，不偽裝成角色沉默，也不無限重試。 |
| AT-15 | Session 用量達上限 | 不再呼叫模型，保留已完成訊息並產生可用收尾。 |
| AT-16 | 重複送出開始／同一回合 | Session 與計費請求不重複，對話事件不重複提交。 |
| AT-17 | 模擬角色答應升遷／離席 | 真人 `observations` 與 person fact 不變；後續檢索也不引用模擬作事實。 |
| AT-18 | 玩家在劇場沉默或反問 | 不自動生成使用者長期人格標籤或 Self Insight。 |
| AT-19 | 人物觀測被撤回 | 新 Session Context 不引用撤回的觀測與舊快取。 |
| AT-20 | 進階模式入口 | 顯示「規劃中」，不可假裝可啟動、付費或保證發佈時間。 |

### 11.1 UX 測試建議

用少量目標使用者驗證：能否自行建場、是否知道何時可介入、是否覺得人物有獨立立場、是否把模擬當真實預測、是否能理解沉默／技術錯誤差異。觀察完成率、操作中斷點、自由輸入負擔與回顧價值。**此項尚未執行。**
